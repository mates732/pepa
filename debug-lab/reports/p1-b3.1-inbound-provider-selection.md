## Detailed Findings

### 1. Resend Inbound

#### Confirmed Capabilities
- **Headers preserved**: Webhook payload includes `message_id` (RFC Message-ID), and `email.received` event triggers → call `resend.emails.get(email_id)` to retrieve full headers including `In-Reply-To`, `References`, full MIME
- **Webhook format**: POST with Svix signatures (`svix-id`, `svix-timestamp`, `svix-signature`); payload has `email_id`, `created_at`, `from`, `to`, `message_id`, `subject`, `attachments[]`
- **Body retrieval**: Webhook only has metadata; call `GET /emails/{email_id}` for full content (HTML, text, headers, attachments)
- **Authentication**: Svix HMAC-SHA256 via `resend.webhooks.verify({ payload, headers, webhookSecret })`
- **DNS**: Add MX record for subdomain (e.g., `replies.pepa.example.com`); Resend provides exact values
- **Free tier**: 3,000 emails/month, 100/day, 3 domains — sufficient for PEPA (single operator, ~100 replies/mo)
- **Retry**: Exponential backoff (configurable max retries); dead-letter queue after max retries
- **Gmail forwarding**: Operator creates Gmail filter: "Has: In-Reply-To" → Forward to `anything@replies.pepa.example.com`

  const signature = req.headers.get('svix-signature');

  if (!id || !timestamp || !signature) {
    return NextResponse.json({ error: 'Missing Svix headers' }, { status: 400 });

      payload,
      headers: { id, timestamp, signature },
      webhookSecret: process.env.RESEND_WEBHOOK_SECRET!,

### 2. Cloudflare Email Routing + Workers

#### Confirmed Capabilities
- **Headers preserved**: Email Worker receives `ForwardableEmailMessage` with full `headers` (Headers object), `raw` (ReadableStream), `messageId`, `from`, `to`, `replyTo`, `subject`, `date`
- **Webhook to HTTP**: Worker must `fetch()` your Vercel endpoint; you implement HMAC-SHA256 signing in Worker and verification in Vercel
- **Body parsing**: Use `postal-mime` in Worker to parse raw MIME → extract text, HTML, headers, attachments
- **Authentication**: Custom HMAC-SHA256 (`X-Webhook-Signature` header) with shared secret stored in Worker secrets + Vercel env
- **DNS**: **Must use Cloudflare DNS**; onboarding adds MX + TXT (SPF/DKIM) automatically
- **Free tier**: Email Routing free; Workers: 100,000 requests/day free (sufficient)
- **Retry**: Worker controls — `message.setReject('reason')` re-queues; or store in D1/KV for manual retry
- **Gmail forwarding**: Forward to `replies@yourdomain.com` → Cloudflare MX → Worker → your webhook

#### Implementation Complexity
```
Cloudflare Worker (~100 lines):
  - Parse email with postal-mime
  - Extract headers: message-id, in-reply-to, references
  - Build JSON payload
  - HMAC-SHA256 sign with WEBHOOK_SECRET
  - fetch() to Vercel /api/email/inbound
  - Handle response: setReject() on failure

Vercel webhook (~80 lines):
  - Verify HMAC-SHA256 (constant-time)
  - Match In-Reply-To/References → provider_message_id
  - cancelPending(leadId)
```

**Verdict**: Viable if already on Cloudflare DNS; otherwise adds Cloudflare account + Worker deployment + DNS migration.

### 3. Gmail API Push (Pub/Sub)

#### Confirmed Capabilities
- **Headers preserved**: Notification only contains `historyId`; must call `gmail.users.history.list` + `gmail.users.messages.get` with `format=full` to get `Message-ID`, `In-Reply-To`, `References`, full MIME
- **Webhook format**: Pub/Sub push → POST with Base64-encoded `{"emailAddress": "...", "historyId": "..."}` in `message.data`
- **Authentication**: OIDC token on push subscription; audience = your webhook URL; service account email for auth
- **DNS**: No custom receiving domain — watches actual Gmail mailbox (operator's personal/work Gmail)
- **Free tier**: Pub/Sub 10 GB/month free; Gmail API free; but requires Google Cloud project + billing enabled
- **Retry**: Pub/Sub exponential backoff; ack deadline 10-600s; dead-letter topic configurable
- **Watch renewal**: Must call `gmail.users.watch` at least every 7 days (recommend daily cron)
- **Gmail forwarding**: **N/A** — watches the actual mailbox; no forwarding needed

#### Implementation Complexity
```
Google Cloud Setup:
  - Create project, enable Gmail API + Pub/Sub API
  - Create Pub/Sub topic + push subscription (OIDC auth to Vercel endpoint)
  - Grant gmail-api-push@system.gserviceaccount.com Pub/Sub Publisher role
  - OAuth consent screen (sensitive scope: gmail.modify)
  - Domain verification (required for gmail.modify on production)

PEPA Implementation:
  - OAuth flow to get refresh token for operator's Gmail
  - Daily cron: gmail.users.watch({ topicName, labelIds: ['INBOX'] })
  - Webhook: decode Pub/Sub message → history.list → messages.get (format=full)
  - Extract Message-ID, In-Reply-To, References from payload
  - Match → cancelPending(leadId)
  - Acknowledge Pub/Sub message (200 OK)
```

**Verdict**: Overkill for PEPA. Requires Google Cloud project, OAuth consent screen, domain verification, daily watch renewal cron, and multiple API calls per notification. Only justified if PEPA also needs **automatic outbound sending** via Gmail API.

## Recommendation: **Resend Inbound**

### Reasons
1. **Lowest complexity** — Native webhook pattern matches existing Telegram webhook architecture
2. **No DNS migration** — Works with current DNS provider; just add one MX record for subdomain
3. **Free tier sufficient** — 3,000 emails/mo >> expected ~100 replies/mo
4. **Header preservation** — Full RFC headers available via `emails.get` API
5. **Vercel-native** — Next.js route, Svix SDK works in Edge runtime, no cross-platform Worker
6. **Operator-friendly** — Gmail filter "Has: In-Reply-To" → Forward to `replies@subdomain.pepa.example.com`
7. **Retry built-in** — Exponential backoff, dead-letter queue, no custom retry logic needed
8. **Local dev** — ngrok tunnel to local `/api/email/inbound` works immediately
